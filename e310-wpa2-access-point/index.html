Why Wi-Fi needs
a real-time radio

An ordinary buffered SDR can send Wi-Fi packets and still miss the ACK deadline. Here is the FPGA path that closes it, and the C++ stack that carries a client from association to HTTP.

You connect an SDR to a Linux computer, generate a Wi-Fi beacon, and see the network name on your phone. The waveform works. Now the phone sends a frame addressed to your access point. Your receiver decodes it, your software constructs an acknowledgment, and your SDR transmits it. The acknowledgment is correct—and late.

For the 1 Mb/s DSSS radio used here, the immediate reply must begin after a nominal 10-microsecond short interframe space, or SIFS. That interval includes the receive pipeline, the final frame check, the decision to reply, and the transmit path. A sample buffer can consume the interval before the CPU sees the end of the frame.

This is why an ordinary buffered GNU Radio application is not a drop-in access point for stock Wi-Fi clients. The gr-ieee802-11 project documents the same obstacle: its USRP-to-host round trip cannot deliver ACKs in time; RTS/CTS has the same problem. Transmitting and decoding Wi-Fi packets is only part of implementing the protocol.

The access point below closes that immediate-response path in an FPGA. Windows C++ handles association, WPA2-PSK/AES-CCMP, DHCP, ARP, TCP and HTTP. It serves a page through an E310's I/Q frontend to ordinary Wi-Fi clients, without a Wi-Fi MAC/baseband chip.

The deadline can expire before the CPU gets the data

A unicast Wi-Fi acknowledgment says that a particular radio frame arrived intact. Before sending one, the receiver must check the destination and the frame check sequence, or FCS. The FCS is at the end of the frame. Earlier bytes reveal whom to acknowledge, but cannot establish that the remaining bytes will arrive correctly.

Receive processing can run while the frame arrives. There is no need to wait for a complete packet before correlating samples, recovering bits or accumulating the FCS. Nevertheless, the final validity decision depends on the end of the incoming signal. Start the timing budget there:

last incoming symbol
  → remaining receive / FCS work
  → decision becomes visible to the response controller
  → transmit trigger and radio-path delay
  → first outgoing ACK preamble symbol

Every delay on this causal path must fit the SIFS budget.

Consider a receiver delivering only completed blocks of 256 complex samples at 20 MS/s. A block occupies 12.8 µs. If the decisive sample lands first in a block, the interface collects another 255 samples before releasing it: 255 / 20,000,000 = 12.75 µs. The nominal 10 µs reply point has passed before software can examine that sample, even if the computation itself takes zero time.

The conclusion follows directly: a response that depends on unavailable data cannot be validly issued before that data becomes available. This particular interface cannot meet the nominal deadline for every frame alignment. A faster CPU cannot remove time already spent waiting at the interface.

Throughput measures something else. At 20 MS/s, signed 16-bit I plus signed 16-bit Q requires 80 MB/s in each direction. Sustaining that rate prevents a growing backlog. It does not guarantee delivery of the last few samples within a microsecond. Larger buffers often improve throughput by amortizing transfers while making this response latency worse.

On PlutoSDR, streaming through USB adds transport and host buffering to the loop. Moving computation onto the E310's nearby ARM removes the Windows/USB leg, but not automatically the receive FIFO, DMA completion policy, cache synchronization, software dispatch or transmit queue. The relevant distance is elapsed time through those interfaces, not millimeters between the ARM and FPGA on a Zynq die.

Linux also need not run the receiving thread immediately. A flowgraph's work batch, another scheduled task, an interrupt or a driver queue can delay it. Removing one source of delay does not bound the rest. A precomputed ACK saves waveform-generation time, but still needs a timely trigger conditional on the received FCS. A timestamp can describe the desired transmit time; it cannot make a late command arrive earlier.

SIFS specifies when the response starts, not when it finishes. A long-preamble 1 Mb/s ACK takes 192 µs of preamble and PHY header plus 112 µs for its 14-byte MAC frame. Its transmission lasts 304 µs. The difficult requirement is starting that transmission after the short gap—not squeezing 304 µs of waveform into 10 µs.

Ten microseconds is a protocol choice, not a law of radio

Wi-Fi shares a channel. A receiver answering the preceding frame gets priority over stations trying to begin a new exchange. The immediate response uses SIFS; a new ordinary DCF transmission waits a longer DIFS and random backoff. For legacy DSSS, a 20 µs slot makes DIFS 10 + 2 × 20 = 50 µs. The ordering protects the current exchange from fresh contenders. RFC 8325 explains the interframe and contention timers.

That ordering does not, by itself, derive the number ten. The May 1995 timing proposal, IEEE 95/81, explicitly distinguishes fixed air-interface intervals from implementation-dependent delays inside a device. Its proposed DS timing table includes a 10 µs maximum. The joint PHY discussion recorded in IEEE 95/91 describes SIFS as receive delay, MAC processing and RX-to-TX turnaround; that meeting gives the frequency-hopping PHY a different budget. These are engineering allocations, not a universal limit imposed by 2.4 GHz propagation.

The subsequent 802.11b draft's PHY table specifies 10 µs SIFS and less than 5 µs receive-to-transmit turnaround. Once a client implements that timing, an access point cannot unilaterally substitute a leisurely software response. The peer's expectations and the channel-access rules still apply. Longer gaps are possible in a differently agreed protocol, at a cost in airtime and latency; they are not a compatible setting that this AP can force onto an unmodified phone.

Other SDR builders hit the same barrier

Shono and colleagues reported it in their 2005 paper, IEEE 802.11 wireless LAN implemented on software defined radio with hybrid programmable architecture. Their VME transfer of a 1,500-byte frame took 40 µs, and the VxWorks interrupt response took 3 µs. They lengthened interframe timing to operate the prototype. That is a concrete published account of the implementation barrier—and of changing the protocol timing rather than meeting the stock-client requirement.

I consider this a substantial cost of the standard's design. A programmer with an I/Q radio cannot replace the Wi-Fi stack as readily as an ordinary network application: the replacement also needs control over microsecond-scale execution and sample delivery. Closed chip firmware makes that dependency harder to escape. A useful challenge to standards designers is to explain the efficiency gained by this timing budget against the implementations it excludes, and whether a negotiable slower-response mode could preserve useful service. Explaining why responses need priority is not the same as proving that exactly 10 µs was the only possible choice.

SIFS is not a WPA2 security check. It predates WPA2. Removing encryption would not remove the acknowledgment deadline.

What a CPU implementation would have to change

A CPU is not forbidden from running these algorithms. It must receive the decisive samples, finish the remaining work and trigger the radio within the actual budget. This requires a bounded low-latency I/O path and execution that cannot be displaced at the wrong moment—not just enough average instructions per second.

Microsoft's Sora paper describes the specific changes: dedicated CPU cores, a custom PCIe radio-control board with a Virtex-5 FPGA and memory, and ACK waveforms prepared or cached on that board before the incoming frame ends. After checking the frame, software triggers the stored reply. The paper also discusses late replies on an initial short frame without a cached ACK. This is evidence for a deliberately engineered CPU processing path, not evidence that loading GNU Radio on an ordinary Linux desktop with a stock buffered SDR meets the same deadline.

The CPU-only E310 work did not produce the required end-to-end stock-client AP. The supplied working implementation therefore keeps the receive-to-ACK path in the FPGA. Its need for that path is an architectural result; it does not establish a physical impossibility for every processor and every possible interface.

Put the deadline-bound path next to the samples

An FPGA runs clocked circuits concurrently. The correlator can accept the next sample while the differential decoder handles a previous symbol, the CRC circuit consumes a previous bit, and the transmit scheduler counts toward a reply. Registers make each stage's latency explicit. None of those circuits waits for a Linux thread to be scheduled.

In this AP, the FPGA receives the sample stream continuously, decodes the frame, checks its FCS and destination, and starts an ACK or CTS locally. It also puts received bytes in a FIFO for software. Copying those bytes to Windows can take much longer than SIFS because the acknowledgment has already been handled.

The E310 reference image uses 2,774 LUTs, 5,185 flip-flops, 14.5 block RAMs and no DSP blocks. Those totals cover the complete image, not a 10 µs timer alone. The radio logic runs at 40 MHz; the processor interface runs at 100 MHz. A flip-flop stores a bit of state or pipeline data, and a LUT implements a small Boolean function. This design spends them on continuously running receive arithmetic, state, buffering, control and sample playback.

The ordinary transmitter does not need to generate a reply to an unknown frame within SIFS. Windows can format it ahead of time and supply a compact waveform description. Conversely, moving only an ACK timer into the FPGA would leave the timer waiting for a late host decision. Receive decoding, final FCS and minimal frame classification belong in the same deadline-bound path in this architecture.

WPA2, DHCP and HTTP remain C++. They need correct state transitions and retries, not a ten-microsecond response to the last RF symbol. The E310 ARM is a packet-and-register adapter in this partition. It does not run the web protocol or hold the station keys.

From I/Q samples to a valid frame

The PHY uses 1 Mb/s differential binary phase-shift keying, or DBPSK, spread with an 11-chip Barker sequence. Each information bit occupies 1 µs. The 20 MS/s interface represents that interval with 20 complex samples. The receiver first asks which sample windows resemble the expected Barker pattern.

C[n] = Σ k=0..19 b[k] × r[n − (19 − k)]
b[k] = the sampled Barker pattern, with coefficients +1 or −1

D[n] = Re{ C[n] × conjugate(C[n − 20]) }
     = I[n] × I[n − 20] + Q[n] × Q[n − 20]
scrambled_bit = sign(D[n])

The first expression correlates the incoming complex samples with the known spread symbol. Because each coefficient is a sign, its multiplication is an addition or inversion. The second expression compares consecutive symbols: matching phase and reversed phase produce opposite signs. Differential detection recovers the phase change without requiring the transmitter and receiver to share an absolute carrier phase.

The sample phase is initially unknown. The receiver maintains correlation scores for all 20 possible symbol alignments, then selects a recurring strong phase. One selected differential/descrambler context follows the long preamble. Recognizing the start-frame delimiter locks that context through the packet. Results still in flight from an abandoned phase are discarded.

The descrambler reverses the seven-bit feedback scrambling. The six-byte physical-layer convergence procedure, or PLCP, header then identifies the rate and packet length. Its CRC must pass before the receiver accepts the declared PSDU, the MAC frame carried inside the physical packet. Byte assembly and the MAC CRC32/FCS calculation continue as its bits arrive.

Serial arithmetic instead of a parallel DSP multiplier

The differential expression needs two signed 18×18 products and their sum. gf_serial_differential.sv schedules one operation every 40 clocks. At 40 MHz that supplies one decision per microsecond. Brian Greenforest's LSB-first serial multiplier and serial adders consume operand bits on successive clocks, with registered partial-product reductions. The graph uses the available clocks within a symbol instead of allocating a wide parallel multiplier.

The correlator has a signed 24-bit path; the differential input stage shifts by three and supplies signed 18-bit operands. gf_serial_mul40.sv handles signed operands and the 40-clock word framing. Word phase, validity and decision age travel beside the arithmetic. A pipeline register delays those control signals just as it delays a value; otherwise the correct result can be interpreted as the wrong symbol.

From the final FCS bit to ACK

The low-MAC classifier retains the frame type, receiver address, transmitter address and duration. A good FCS and an eligible unicast addressed to this AP permit an ACK. An eligible RTS permits CTS. Broadcast frames do not receive individual ACKs. The ACK's receiver address is the transmitter address of the received frame.

At 40 MHz, 10 µs is 400 clocks. But the decoded end-of-frame event is already some clocks old. The scheduler subtracts that age and the downstream transmit-path offset from the 400-clock target. Starting a fresh 400-clock countdown after decoding would produce a systematically late reply. A late event is rejected rather than treated as if the air-interface clock had restarted.

The local control transmitter creates the ACK or CTS, adds its FCS and emits the DSSS waveform. For CTS, the duration field preserves the remaining reservation after subtracting SIFS and the CTS airtime, clamped at zero. RF disarm or a fault overrides the player. Software must not send a duplicate host-generated ACK; the packet adapter excludes outputs marked for the local SIFS path.

From a software frame to transmitted samples

For an ordinary outgoing frame, Windows starts with a PSDU containing the MAC header, body and four-byte FCS. e310_host_waveform.hpp::encode() builds the physical packet around it:

  1. The long preamble starts with 128 SYNC bits, initially ones, followed by the start-frame delimiter. The stored SFD bytes are A0 F3, sent least-significant bit first.
  2. The six-byte PLCP header contains SIGNAL 0A for 1 Mb/s, SERVICE 00, the little-endian length 8 × PSDU_bytes in microseconds, and a CRC over those first four header bytes. The reflected CRC polynomial is 8408, with initial state FFFF and final complement.
  3. The encoder scrambles the preamble, header and PSDU. With a transmit seed of 5D, it computes s = input_bit XOR state[3] XOR state[6] and shifts in s.
  4. Differential encoding updates phase ^= s. The resulting phase selects the polarity of the spread symbol, using Barker signs + − + + − + + + − − −.
  5. For sample positions 0 through 19, the host selects Barker chip floor(11 × sample / 20). This explicitly maps eleven chips onto twenty samples; it does not assume two samples per chip.

This rectangular waveform has only two complex sample values: I = +8192 or −8192, Q = 0. The WF20 descriptor carries the two packed IQ16 values, a 20-bit polarity pattern, and one differential phase bit per symbol. It describes this waveform exactly; it is not a compression scheme for arbitrary I/Q.

The FPGA player rotates the twenty-position pattern, combines its polarity with the current phase bit, and chooses one of the two sample values. After twenty sample ticks it advances the phase bit. PLCP construction, scrambling and spreading decisions have already happened in C++. This is why ordinary transmit formatting can stay on Windows despite the comparatively slow serial connection.

A packet must play continuously once started. Backpressure cannot stretch an over-air symbol; a stalled output aborts playback. The ordinary transmit queue also remains distinct from the immediate-response engine: an ACK cannot wait behind the next scheduled beacon or HTTP frame.

Let the client discover and join the AP

The reference SSID is PLUTO-2.4, on channel 6. Its beacon advertises the network name, supported rate, channel, timing and RSN security parameters. The supported basic rate is 1 Mb/s with a long preamble. RSN advertises WPA2-PSK with AES-CCMP; it does not advertise modulation or security features the receiver cannot handle.

Discovery, association and encryption are separate transitions:

  1. Discovery. The station hears a beacon or sends a probe request and receives a probe response. A visible SSID proves discovery, not a working return path.
  2. Open-system authentication. The station sends authentication transaction 1; the AP answers transaction 2 with success. This historical name does not make the eventual data network unencrypted. WPA2 key authentication happens later.
  3. Association. The station requests the SSID and compatible rates/security. The AP validates the request, assigns an association ID and returns a successful association response.
  4. Key establishment. The WPA2 four-way handshake proves possession of matching key material and installs traffic keys. Ordinary IP data is not accepted as an alternative to this exchange.

Each station has its own association state, nonce, pairwise key, replay counters and power-save queue. The default capacity is eight stations. A new association must not inherit another station's key or an old session's replay state. The beacon interval is configurable; the supplied host command uses ten time units, or 10.24 ms.

The legacy 1 Mb/s PHY and WPA2-AES are independent choices. A phone may describe the radio as a legacy access point even though the protected data uses AES-CCMP.

Turn the shared password into per-station keys

The AP does not transmit the password. Both peers independently derive a 32-byte pairwise master key, or PMK, using the exact passphrase and SSID bytes:

PMK = PBKDF2-HMAC-SHA1(passphrase, SSID, 4096 iterations, 32 bytes)

A changed SSID changes this key, even with the same password. The AP supplies a fresh 32-byte random ANonce. The station supplies a fresh SNonce. Both peers combine those nonces with their MAC addresses to derive a pairwise transient key, or PTK.

B = min(AP_MAC, STA_MAC) || max(AP_MAC, STA_MAC)
  || min(ANonce, SNonce) || max(ANonce, SNonce)

block[i] = HMAC-SHA1(PMK,
  "Pairwise key expansion" || 00 || B || byte(i))
PTK = first_48_bytes(block[0] || block[1] || block[2])

The comparisons are lexicographic byte comparisons. The first sixteen PTK bytes are the key confirmation key, KCK; the next sixteen are the key encryption key, KEK; the final sixteen are the temporal key, TK, for pairwise CCMP traffic.

MessageWhat it carries and establishes
M1: AP → stationANonce and an EAPOL replay counter. The station now has the inputs needed to derive PTK.
M2: station → APSNonce, negotiated security information and a MIC computed with KCK. The AP derives the same PTK and verifies the MIC.
M3: AP → stationKey-install information and the group temporal key, encrypted with KEK, plus a KCK MIC and the expected replay-counter progression.
M4: station → APA MIC-protected acknowledgment confirming the handshake. The station can now exchange protected data.

For the WPA2 descriptor version used here, the MIC is the first sixteen bytes of HMAC-SHA1 over the complete EAPOL packet with its MIC field zeroed. It is not computed over the outer Wi-Fi header. The AP must preserve the handshake's nonce and key state across retransmissions rather than inventing new keys each time M3 is sent.

The group temporal key, GTK, is a random sixteen-byte AES key. M3 wraps its key-data element using the separate AES key-wrap construction. Group traffic uses a key shared with the group's members; it is not private from other holders of that GTK. Pairwise traffic uses each station's TK.

The implementation can also recognize authenticated, non-replayed CCMP traffic under the newly established TK as key-install confirmation if M4 was missed. That requires a previously verified M2 and a valid authentication tag—not merely bytes resembling DHCP. Windows uses BCrypt for cryptographic operations and randomness; the non-Windows branch uses OpenSSL.

A phone's password error is not a packet trace. It can follow a failed handshake exchange. Debug the exact SSID/key bytes, M2 MIC, M3 wrapping and replay counters, and whether the radio delivered each message.

Open the encrypted frame before parsing IP

A protected data frame is arranged as MAC header, eight-byte CCMP header, encrypted LLC/payload, eight-byte authentication tag and four-byte FCS. The FCS detects radio corruption. The CCMP tag authenticates the protected contents and selected header fields. A valid FCS does not establish a valid cryptographic tag.

CCMP uses a 48-bit packet number, PN, to build a unique nonce. The thirteen-byte nonce consists of priority, transmitter MAC address and PN bytes in the specified order. Non-QoS traffic uses priority zero; QoS uses its traffic identifier. The authenticated header data masks fields that can change during delivery, rather than copying the entire MAC header verbatim.

On receive, C++ parses the actual header length, selects the station key, constructs the nonce and additional authenticated data, and verifies AES-CCM. It then enforces the authenticated packet number against the station's replay state before delivering plaintext. There are separate counters for sixteen QoS queues and the non-QoS queue. A bad tag must never advance a replay counter.

A duplicate radio frame may still need a low-level ACK, but its payload must not reach TCP twice. Every newly encrypted outgoing frame receives a fresh PN; exhaustion is an error, not wraparound. Uplink and downlink also have different address roles. The CCMP nonce uses the transmitting station's address, not whichever address happens to be first in the header.

Inside the decrypted payload, LLC/SNAP starts with AA AA 03 00 00 00 and a two-byte EtherType. 888E identifies EAPOL, 0806 ARP, and 0800 IPv4. That dispatch is where received Wi-Fi bytes become the network protocols the application expects.

Give the station an address and a server to reach

The C++ endpoint owns 192.168.44.1/24. Station leases begin at 192.168.44.100. These are addresses in the protocol engine, not addresses assigned to a Windows Ethernet adapter.

For DHCP, the station sends DISCOVER on UDP port 68 to port 67. The parser checks the BOOTP request structure and DHCP cookie, then reads the transaction ID and options. The AP offers a lease; the station requests it; the AP returns DHCP ACK with the matching transaction, server address, subnet mask, lease time and local DNS information. Requests selecting a different server are ignored.

The DHCP reply's IPv4 destination can be broadcast while its enclosing Wi-Fi frame is pairwise-encrypted unicast to the requesting station. IP addressing and radio addressing are separate layers. This delivery path does not require a sleeping group of clients to receive a broadcast simultaneously.

Next the station asks ARP which hardware address owns 192.168.44.1. The AP replies with its MAC address inside a protected data frame. The station can now send an IP packet to the web endpoint. The local DNS responder returns the AP address for captive discovery, and ICMP echo is supported. Neither provides an internet uplink.

IPv4, UDP and TCP fields use network byte order. The generated IPv4 header has its own checksum; UDP and TCP also include the IP pseudoheader in their checksums. Those checks are separate from the PHY-header CRC, Wi-Fi FCS and CCMP tag.

Source: IPv4/UDP construction, DHCP, ARP, DNS and ICMP.

Deliver the HTML as a TCP byte stream

The web server is not a Windows socket listening on port 80. process_tcp() receives an IPv4 payload from the decrypted Wi-Fi frame and constructs the reply segments itself. A browser on the RF network opens http://192.168.44.1/; a computer on an unrelated wired network does not reach this endpoint.

A connection record identifies the station and client source port. An incoming SYN consumes one client sequence number. The AP sends SYN+ACK; the client's acknowledgment establishes the connection. The parser respects the TCP data-offset field, because options can make the header longer than twenty bytes.

The HTTP request may cross several TCP segments. The server appends in-order bytes and acknowledges the cumulative position until it has the header terminator \r\n\r\n. Duplicate bytes are not a second request. GET returns a status line, content type, content length and the configured HTML; HEAD omits the body. The reference limits the page to 1,400 bytes.

The response is sent with ACK, PSH and FIN. Sequence accounting includes the response bytes and one additional position for FIN. If the client only acknowledges part of the response, the retained TCP state sends the remaining tail. A retry preserves the TCP byte positions but uses a fresh CCMP packet number for its newly encrypted Wi-Fi frame.

Response retransmission starts with a one-second timeout, backs off to a maximum of sixty seconds, and has a bounded attempt count. An in-window reset cancels the connection and deferred response. A client ACK covering the bytes and FIN completes the TCP response; putting samples into a radio FIFO does not.

Handle a client that stops listening

A phone may set its Power Management bit and sleep between beacon intervals. The AP buffers unicast data and marks the station's association ID in the beacon's traffic indication map, or TIM. A PS-Poll releases a queued frame, with More Data indicating whether anything remains. An awake indication lets the AP flush pending delivery.

The More Data flag is excluded from CCMP's authenticated header fields, so it can be updated on a buffered frame while retaining its ciphertext; the outer FCS must be recomputed. HTTP retries also need to distinguish a frame waiting in the sleeping client's queue from a frame that was actually transmitted.

The source implements the complete page-fetch path. The compact FPGA revision delivered HTTP 200 and all 491 expected body bytes to an ESP8266 station; the FPGA-assisted stack also served the page to an iPhone. The implementation record keeps the revision-specific results separate from the protocol explanation.

This is a compact local endpoint, not a complete production router: it has no NAT, IPv6, IP fragment reassembly or arbitrary-length HTTP streaming. Its simplified DHCP INFORM handling and receive-side IP/transport validation need extension for a general-purpose network product.

Source: TCP state, HTTP response, retransmission and power-save queues.

Carry frames across the host boundary

Windows and the E310 ARM exchange binary messages over a 460800-baud serial link. With 8N1 framing, even one serial byte takes about 21.7 µs. This connection plainly cannot carry an end-of-frame decision to Windows and return an ACK trigger within SIFS. It carries ordinary frames, receive events, configuration and health messages after the FPGA handles the immediate radio response.

The GFAP wire header contains version, kind, payload length, session ID, sequence number and CRC32. COBS encoding removes internal zero bytes; a zero byte terminates each encoded message. Size, signature, CRC, session and sequence checks prevent corruption or stale transport data from becoming a valid current command.

The adapter announces itself, accepts initialization, and reports its radio capabilities. WF20 selects host-generated waveform descriptions; EV10 supplies byte events with frame-boundary markers; CR11 supplies raw counter words. Windows assembles PSDUs and interprets those counters. A missing event batch breaks the partial frame rather than splicing two different packets together.

A two-second host lease is enforced on the radio side. STOP disables RF before reporting STOPPED, and host loss must not leave a transmitter running indefinitely. This is a local fault-response contract, separate from the much shorter ACK contract.

Source: complete wire format · receive assembly · Windows packet core · ARM packet adapter.

Move the implementation without moving the deadline

The protocol boundary is a complete received PSDU. ApProtocol::ingest() consumes it and produces outgoing frames; maintenance(now) advances retries and deferred work; beacon(timestamp) constructs discovery traffic. A processor port supplies monotonic time, cryptographic randomness, AES/HMAC operations and storage. It can run those functions on Windows, ARM or another suitable processor without changing the air protocol.

The radio boundary has a stricter contract: continuous signed I/Q, known sample timing, decoded frame boundaries with their age, and an immediate-response path. Changing sample rate requires changing the Barker sample mapping, phase selection and cycle calculations together. Changing an API name or a clock constant is not a PHY port.

For another SDR or custom chip, first implement the sample path and measure the first ACK sample relative to the received frame's end. Then attach the software packet engine. For another FPGA, preserve the serial arithmetic's word phase and registered control delays when mapping its memories, clocks and I/O. An ordinary sample player is sufficient for prepared transmit traffic; it is not sufficient by itself for valid frame-dependent replies.

The E310-specific shell supplies PS7 register access, asynchronous FIFOs, RFIC I/O and clocks. Its processor AXI clocks remain running independently of radio activity. Those plumbing details are replaceable. The requirement that the final FCS decision reaches a ready transmitter on time is not.

Build and run the reference

The source archive contains the C++ protocol and crypto, receiver and serial arithmetic, ACK/CTS engine, waveform player, transport, E310 shell, constraints and build scripts. The inline browser embeds every source file with individual downloads.

Unzip into a writable directory. With MSVC C++ Build Tools and CMake 3.24 or newer, run these commands from a normal Windows command prompt:

build-windows.cmd
wifi_e310_link\build\windows-packets\gf_e310_windows_ap.exe --help

The build includes protocol, transport, receive-event and host-core tests without opening a radio. For the E310 FPGA image, run:

powershell -NoProfile -ExecutionPolicy Bypass -File build-e310-fpga.ps1 -Vivado C:\VitisVivado\2026.1\Vivado\bin\vivado.bat

The script selects the compact implementation and produces the bitstream, utilization and timing reports; it does not program the board. The reference targets xc7z020clg484-3 and the E310's legacy Linux 3.14/UHD 3.10.1.1 device interface. A newer MPM image needs a matching board adapter, not this shell loaded blindly into it.

Build the ARM adapter using build-arm.sh with a C++20 ARM Linux toolchain. The supplied README gives the tested E310 SDK environment command. Keep its matching loader/runtime in a project directory rather than replacing the board's system C library.

Bring up the radio side first

The reference's device setup order is: arm the independent processor watchdog guard; load the stock radio image; initialize the RF device with legacy UHD while retaining that device owner; set the receive delay; load the custom image; verify its registers and processor-management access; initialize the RFIC against that shell; arm capture; start the packet agent; hand the serial connection to Windows. The archive retains the setup and recovery helpers. On stop, disable RF, restore the stock image, release the device owner, then disarm the guard after recovery.

This is board-specific setup, not a function performed by the Windows launcher. Once the compatible packet adapter is running, close any other terminal using its COM port. Create a UTF-8 text file without a BOM containing your chosen 8–63-byte passphrase, then run:

run-host.cmd COM10 C:\radio-config\ap.key

Replace COM10 with the adapter's port. Join PLUTO-2.4 using the same passphrase and open http://192.168.44.1/. The example page is included. Native options configure SSID, channel, server IP, station count, page, beacon interval and a stop file. Ctrl+C requests RF shutdown; a lost host connection expires the local lease.

Source and algorithm references

The selected PHY uses Barker DSSS and DBPSK, not OFDM, CCK, Viterbi or Reed–Solomon. Greenforest's implementation is MIT-licensed. The bundle retains the separate LGPL notices on Ettus FPGA helpers and GPL notices on the RFIC calibration driver.

FIPS 197 specifies AES. RFC 3610 §9 records the CCM authors' public-domain dedication and their statement that they knew of no covering patents. That is a specific rights statement, not evidence that every part of Wi-Fi has universal patent clearance. The algorithm and patent appendix separates the implemented methods, patent records and source licenses.

The source lets you change the packet engine without reimplementing the radio, or replace the radio while keeping association through HTTP. The boundary to preserve is precise: received frame validity must reach a ready local reply path within SIFS. Everything above it can use the processor and software environment appropriate to the application.
